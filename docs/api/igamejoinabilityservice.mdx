# IGameJoinabilityService

The `IGameJoinabilityService` is a sealed interface that defines the contract for determining whether a viewer can join a game. It provides methods for both single game and batch joinability computations, taking into account participant counts and user-specific constraints.

## Purpose

This interface serves as the core abstraction for game joinability logic in the UpMatches application. By using a sealed interface, it restricts implementation to only the `GameJoinabilityService` class, ensuring controlled and consistent joinability calculations across the system.

## Interface Definition

```java
public sealed interface IGameJoinabilityService permits GameJoinabilityService {
    // Methods defined below
}
```

## Methods

### `compute`

Computes the joinability status for a single game based on the current participant count and the requesting user.

| Parameter | Type | Description |
|-----------|------|-------------|
| `game` | `Game` | The game entity to evaluate joinability for |
| `participantCount` | `long` | Current number of participants in the game |
| `userId` | `UUID` | The unique identifier of the user requesting to join |

**Returns:** `ViewerJoinabilityResponse` - A response object containing the joinability status and any relevant information for the specified user.

### `computeBatch`

Computes joinability status for multiple games simultaneously, allowing for efficient batch processing.

| Parameter | Type | Description |
|-----------|------|-------------|
| `games` | `List<Game>` | A list of game entities to evaluate joinability for |
| `participantCountsByGameId` | `Map<UUID, Long>` | A map associating each game's UUID with its current participant count |
| `userId` | `UUID` | The unique identifier of the user requesting to join |

**Returns:** `Map<UUID, ViewerJoinabilityResponse>` - A map where each key is a game UUID and the value is the corresponding `ViewerJoinabilityResponse` for that game.

## Implementation Notes

- The interface is sealed, meaning only `GameJoinabilityService` can implement it
- Both methods require a `userId` parameter, indicating joinability decisions are user-specific
- The batch method accepts participant counts as a separate map, allowing callers to provide pre-computed or cached participant data
- The `ViewerJoinabilityResponse` type encapsulates the result of the joinability check, including whether the user can join and any relevant constraints or messages

## Usage Example

```java
// Single game check
ViewerJoinabilityResponse response = joinabilityService.compute(
    game, 
    game.getParticipantCount(), 
    currentUserId
);

// Batch check for multiple games
Map<UUID, Long> participantCounts = games.stream()
    .collect(Collectors.toMap(Game::getId, Game::getParticipantCount));
    
Map<UUID, ViewerJoinabilityResponse> responses = joinabilityService.computeBatch(
    games,
    participantCounts,
    currentUserId
);
```
