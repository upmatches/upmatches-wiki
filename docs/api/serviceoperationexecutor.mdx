# ServiceOperationExecutor

## Purpose

The `ServiceOperationExecutor` is a utility class that provides a standardized way to execute service operations with comprehensive error handling, logging, and tracing. It wraps business logic execution with consistent exception management for database operations, REST client calls, and runtime errors. The class automatically generates or propagates trace IDs for request tracking and provides detailed logging at each step of execution.

This class is designed to be used as a static utility, not instantiated, and provides two main execution methods: one for operations that return a value and one for void operations.

## Public Methods

### `execute`

Executes a supplier operation with comprehensive error handling and tracing.

| Parameter | Type | Description |
|-----------|------|-------------|
| `operation` | `Supplier<T>` | The operation to execute, wrapped as a supplier |
| `operationType` | `OperationStatus` | The type of operation being performed (e.g., SAVE, RETRIEVE, UPDATE, DELETE) |
| `exceptionFactory` | `ExceptionFactory` | Factory for creating domain-specific exceptions |

**Returns:** `T` - The result of the operation

**Throws:**
- `IllegalArgumentException` - If the operation receives invalid arguments
- `ExternalServiceException` - If a REST client call fails
- `ResourceNotFoundException` - If a requested resource is not found
- `InvalidFileException` - If an invalid file is encountered
- Various database-related exceptions mapped through the `ExceptionFactory`

**Example:**
```java
User user = ServiceOperationExecutor.execute(
    () -> userRepository.findById(userId),
    OperationStatus.RETRIEVE,
    exceptionFactory
);
```

### `executeVoid`

Executes a void operation (Runnable) with the same error handling and tracing as `execute`.

| Parameter | Type | Description |
|-----------|------|-------------|
| `operation` | `Runnable` | The void operation to execute |
| `operationType` | `OperationStatus` | The type of operation being performed |
| `exceptionFactory` | `ExceptionFactory` | Factory for creating domain-specific exceptions |

**Throws:** Same as `execute` method

**Example:**
```java
ServiceOperationExecutor.executeVoid(
    () -> userRepository.deleteById(userId),
    OperationStatus.DELETE,
    exceptionFactory
);
```

## Internal Behavior

### Trace ID Management

The class manages trace IDs through SLF4J's MDC (Mapped Diagnostic Context). It checks for an existing trace ID in the MDC context and generates a new UUID if none exists. The trace ID is automatically cleaned up from MDC after operation completion if it was created by this executor.

### Exception Handling Flow

The exception handling follows a hierarchical approach:

1. **IllegalArgumentException** - Logged and rethrown as-is
2. **DataAccessException / PersistenceException** - Delegated to `handleDatabaseException()`
3. **RestClientException** - Delegated to `handleRestClientException()`
4. **InvalidFileException** - Wrapped using the exception factory
5. **ResourceNotFoundException** - Logged and rethrown as-is
6. **RuntimeException** - Checked for programmer errors (NullPointerException, IllegalStateException, etc.) or wrapped using the exception factory

### Database Exception Handling

Database exceptions are categorized and handled as follows:

| Exception Type | Handling |
|---------------|----------|
| OptimisticLockingFailureException | Concurrent modification detected |
| DeadlockLoserDataAccessException | Database deadlock detected |
| CannotAcquireLockException | Cannot acquire database lock |
| PessimisticLockingFailureException | Resource locked by another transaction |
| EntityNotFoundException | Mapped based on operation type (RETRIEVE, UPDATE, DELETE) |
| EntityExistsException | Entity already exists |
| DataIntegrityViolationException | Mapped based on operation type |
| ConstraintViolationException | Mapped based on operation type |
| InvalidDataAccessResourceUsageException | Analyzes root cause for table/column/syntax errors |
| JpaSystemException | JPA system error |
| InvalidDataAccessApiUsageException | Invalid data access API usage |
| PersistenceException | Persistence error |

### REST Client Exception Handling

REST client exceptions are handled based on their type:

| Exception Type | Handling |
|---------------|----------|
| HttpStatusCodeException | Creates ExternalServiceException with status code and truncated response body |
| ResourceAccessException | Creates ExternalServiceException indicating service unavailability |
| Other RestClientException | Creates ExternalServiceException with generic error message |

### Response Body Truncation

Response bodies from HTTP status code exceptions are truncated to a maximum size (defined in constants) to prevent memory issues. A truncation indicator is appended to truncated responses.

## Usage Guidelines

1. **Always provide an ExceptionFactory** - This ensures consistent exception types across your application
2. **Use appropriate OperationStatus** - This affects how database exceptions are mapped to user-friendly messages
3. **Handle ExternalServiceException** - REST client calls can fail with network issues or service unavailability
4. **Consider trace ID propagation** - The executor respects existing trace IDs, allowing for distributed tracing

## Dependencies

- SLF4J for logging
- Spring Framework's DataAccessException hierarchy
- Hibernate's ConstraintViolationException
- Jakarta Persistence exceptions
- Custom exception types (ExternalServiceException, InvalidFileException, ResourceNotFoundException)
- Custom constants class (ServiceOperationExecutorConstant)
